# AI Hot Monitor 需求说明

## 1. 项目目标

面向 AI 学习者，自动发现并监控指定领域内的热点变化，减少人工检索成本，并在热点出现的第一时间通过浏览器实时推送和邮件通知用户。

项目优先级：

1. 先完成可用的 Web 版。
2. Web 版验证可用后，再封装为 Agent Skill。
3. 以轻量、敏捷、可快速迭代为导向，避免过度工程化。

## 2. 核心用户故事

### 2.1 关键词监控

作为用户，我可以输入要监控的关键词或主题范围，例如：

- `GPT-5 release`
- `AI 编程`
- `Claude Code`
- `OpenAI agent`

系统需要自动从多个信息源中持续搜索相关内容，并在发现真实、可信、且确实相关的内容后立即通知我。

### 2.2 热点发现

作为用户，我可以配置一个兴趣范围，例如 `AI 编程`、`大模型`、`Agent`、`开源模型`，系统需要定时主动发现该范围内的新热点，而不只是等待精确关键词命中。

### 2.3 热点真假识别

作为用户，我不希望收到假冒、蹭热点、误导标题、搬运拼接的内容。系统需要借助 AI 对抓取结果做二次判定，输出：

- 是否真实相关
- 是否可能是假冒或标题党
- 是否来自官方或高可信来源
- 热度评分
- 摘要与原因说明

### 2.4 实时提醒

作为用户，我希望在热点出现时，系统能及时提醒我，包括：

- 浏览器实时推送
- 邮件通知

### 2.5 可视化查看

作为用户，我希望在响应式 Web 页面中查看：

- 当前监控任务
- 实时发现的热点流
- 每条热点的可信度、热度、来源、时间
- 通知发送记录

### 2.6 Agent Skill 封装

作为用户，我希望在 Web 版稳定后，把这套能力进一步封装成 Agent Skill，供其他 AI 代理直接调用。

## 3. 信息源范围

系统必须支持多源并行获取信息，避免依赖单一数据源。

当前确认的信息源：

1. `Bing` 搜索结果页抓取
2. 百度搜索结果页抓取
3. 微博热搜抓取
4. RSS 订阅源
5. 通用网页抓取
6. Twitter(X) 第三方 API：`twitterapi.io`

## 4. 关键约束

### 4.1 Bing Search API 已退役

需要特别记录：官方 `Bing Search API` 已于 `2025-08-11` 退役。当前时间为 `2026-04-21`，不应基于该退役接口设计新项目。

因此项目中对 Bing 的接入策略改为：

- 默认方案：`Bing 网页搜索抓取适配器`
- 可选扩展：后续如果用户需要 Azure 路径，可单独增加 `Grounding with Bing Search` 适配层

### 4.2 轻量实现

项目应优先使用：

- 轻量服务端结构
- 尽量少的依赖
- 可快速调试的本地开发体验

### 4.3 反爬与频率控制

对于百度、微博、Bing 网页结果抓取，需要默认启用：

- 请求频率限制
- 随机抖动
- User-Agent 管理
- 抓取失败回退
- 去重与重试限制

避免对单一站点造成过高访问频率。

## 5. Web MVP 功能范围

Web 第一阶段最小可用版本包含：

1. 监控任务管理
2. 信息源管理
3. 抓取调度器
4. AI 判别流水线
5. 浏览器实时推送
6. 邮件通知
7. 热点流与命中记录页面
8. 基础日志与错误反馈

## 6. 非目标

第一阶段不做：

- 多用户登录与权限系统
- 云端分布式调度
- 大规模采集集群
- 复杂 BI 报表
- Agent Skill Marketplace 发布流程

## 7. 人工确认点

在正式开发完成前，需要用户最终确认以下默认实现：

1. Bing 源使用网页抓取，不再尝试退役的 Bing Search API。
2. 浏览器实时推送使用 `SSE(Server-Sent Events)`。
3. 邮件通知基于 `SMTP`。
4. Twitter(X) 数据通过 `twitterapi.io` 获取。
5. Web 版通过本地持久化数据运行，先不接入复杂数据库。
